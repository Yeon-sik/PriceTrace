# 영수증 로컬 보관과 개인정보 비연결 가격 관측 설계안

| 항목 | 내용 |
| --- | --- |
| 상태 | 제안 (구현 전) |
| 작성일 | 2026-08-01 |
| 적용 범위 | 영수증 OCR 입력, 가격 관측 저장·공개, 제출 인증 및 중복 처리 |
| 이번 문서에서 하지 않는 일 | 코드·스키마·인프라 변경 |

## 1. 목적

PriceTrace는 영수증을 가격의 근거로 사용하되, 서버가 영수증 원본이나
사용자의 구매 이력을 보유하지 않도록 한다. 서버가 다루는 도메인 객체는
`영수증`이 아니라 **판매처에서 특정 날짜에 관측된 상품 가격**이다.

이 설계의 목표는 다음과 같다.

- 영수증 이미지와 전체 OCR JSON은 사용자의 기기에만 남긴다.
- 서버와 공개 화면에서는 한 사람이 제출했는지, 여러 사람이 각각 제출했는지,
  또는 어떤 상품들이 한 장의 영수증에 함께 있었는지를 알 수 없게 한다.
- 공개된 판매처 정보로 가격 관측의 신뢰성과 재현성을 유지한다.
- 인증과 악용 방지는 처리하되, 인증 주체와 저장된 가격 관측을 연결하지 않는다.

## 2. 데이터 경계

### 2.1 사용자 기기에만 보관하는 영수증 원본

OCR이 생성한 전체 JSON, 영수증 이미지, 원문 텍스트, 거래 시각, 결제 정보,
구매자 정보, 거래·승인 번호는 로컬 영수증 레코드에만 보관한다.

로컬 레코드에는 `localReceiptId`를 둔다. 이 ID는 사용자의 기기에서 이미
처리한 영수증인지 판단하고 재등록을 막는 용도이며, 서버에 전송하거나
서버의 가격 관측 ID로 사용하지 않는다.

로컬 원본은 앱 저장소/운영체제 보호 영역에 보관하고, 사용자가 삭제할 수
있어야 한다. 원본의 클라우드 동기화·서버 백업은 이 설계 범위에 포함하지 않는다.

### 2.2 서버에 저장하는 판매처 마스터

판매처 주소는 공개된 사업장·지점 정보이므로 가격 관측의 출처를 설명하기 위해
등록할 수 있다. 다만 영수증 OCR에서 읽은 주소 문자열을 그대로 저장하지 않고,
정규화된 판매처 마스터를 사용한다.

```text
Store
- storeId
- 상호명
- 지점명
- 도로명 주소
- 선택: 공개 지도 POI 식별자 또는 좌표
```

판매처 마스터는 가격 관측과 `storeId`로 연결한다. 영수증, 제출자, 거래 시각은
판매처 마스터에 저장하지 않는다.

### 2.3 서버에 저장하는 가격 관측

서버의 가격 관측은 아래의 최소 필드만 가진다.

```text
PriceObservation
- storeId
- observedOn: YYYY-MM-DD
- 상품 식별 정보: 표준 상품/규격 ID, 또는 정규화 전 상품명과 규격
- unitPriceKrw
```

상품 수량, 영수증 합계, 구매 시각, 영수증 ID, 영수증 항목 ID, 제출자 ID,
제출 시각은 가격 관측의 필드가 아니다. 단가를 정확히 해석할 수 없다면
그 항목은 관측으로 전송하지 않고 로컬에서 수정·확인한다.

## 3. 처리 흐름

```text
영수증 이미지
  -> 기기 내 OCR 전체 JSON
  -> 로컬 영수증(localReceiptId로 재등록 방지)
  -> 필요한 항목만 추출·사용자 확인
  -> 최소 가격 관측 payload 전송
  -> 인증·형식 검증·속도 제한
  -> 인증 정보를 제거한 관측 병합
  -> PriceObservation / Store만 저장·공개
```

인증은 전송을 허용하고 악용을 억제하는 입구의 책임이다. 가격 관측 저장소의
책임은 가격 상태를 보존하는 것이다. 두 책임을 같은 레코드에 저장하지 않는다.

## 4. 중복과 악용 방지의 분리

중복 처리는 서로 다른 세 문제로 나누어야 한다.

| 문제 | 처리 위치 | 기준 | 서버에 남는 것 |
| --- | --- | --- | --- |
| 같은 사용자가 같은 영수증을 다시 선택 | 로컬 | `localReceiptId`와 로컬 처리 상태 | 없음 |
| 네트워크 재시도로 같은 요청이 반복 | 인증 입구 | 짧게 만료되는 요청 idempotency 키 | 짧은 보존의 요청 처리 상태만 |
| 여러 제출이 같은 가격 상태를 가리킴 | 가격 관측 저장소 | `storeId + observedOn + 상품/규격 + unitPriceKrw` | 병합된 가격 관측 하나 |

마지막 병합은 “그 가격이 그날 해당 판매처에서 **적어도 한 번 관측되었다**”는
뜻이다. 제출 수, 영수증 수, 관측 횟수는 저장·표시·집계하지 않는다. 따라서
동일한 가격을 백 명이 제출해도 서버의 공개 가격 데이터는 한 관측으로 남는다.

`가게 이름 + 날짜 + 거래 시각`을 영수증 중복 판정 키로 사용하는 방식은
채택하지 않는다. 서로 다른 사람이 같은 시각대에 구매할 수 있고, 한 사람이
같은 날 여러 번 구매할 수 있으며, 정확한 거래 시각 자체가 불필요한 행동
정보이기 때문이다.

## 5. 인증과 로그 정책

제출을 받는 서비스에는 인증 또는 단기 익명 자격증명, 요청별·기간별 속도 제한,
입력 스키마 검증이 필요하다. 이는 조작·대량 제출을 줄이기 위한 것이지
영수증을 추적하기 위한 것이 아니다.

- 인증 성공 여부와 rate limit은 입구에서만 판단한다.
- 관측을 저장하기 전 인증 주체·세션·IP·요청 시각·원본 payload를 관측 레코드에서 제거한다.
- 접근 로그와 보안 로그에는 원본 OCR JSON, 이미지, 영수증 ID, 전체 관측 payload를 기록하지 않는다.
- 보안상 필요한 IP·세션·요청 로그는 별도 저장소에 최소 기간 보관하고, 가격 관측과 조인할 수 있는 키를 만들지 않는다.
- 관리 화면과 판매처 통계에는 영수증 수·제출자 수·제출 횟수를 제공하지 않는다.

인증 정보와 가격 관측을 장기간 연결해 보관하면, 해당 관측은 다시 사용자
구매 이력으로 해석될 수 있다. 이 연결을 만들지 않는 것이 본 설계의 핵심
프라이버시 경계다.

## 6. 공개 화면 정책

공개 화면은 상품별 가격과 판매처를 보여 줄 수 있다. 판매처는 상호·지점·주소를
포함할 수 있고, 관측 날짜는 일 단위로만 표시한다.

다음 정보는 공개하지 않는다.

- 영수증 이미지·원문 OCR·영수증 번호·결제 정보
- 거래 시간 또는 업로드 시간
- 한 장의 영수증에 포함된 다른 상품
- 해당 판매처의 영수증 수, 제출 수, 제출자 수

관측이 매우 희소한 민감 판매처는 공개 지연 또는 더 넓은 지역 단위 표시가
필요한지 별도 정책으로 검토한다.

## 7. 예외 처리와 금지 경계

예외 상황도 영수증 원본을 서버에 올리는 근거가 되지 않는다. 아래 경우에는
로컬에서 처리하거나, 최소 관측 payload와 분리된 보안 절차를 사용한다.

| 상황 | 처리 | 서버에 영수증 원본을 저장하지 않는 이유 |
| --- | --- | --- |
| OCR이 날짜·상품·단가를 확정하지 못함 | 로컬에서 사용자 수정·재촬영·전송 보류 | 원문을 받지 않아도 품질 문제를 해결할 수 있음 |
| 로컬 중복 여부가 불확실함 | 사용자가 기기에서 원본을 비교·정리 | 거래 시각·영수증 지문을 서버 중복 키로 만들지 않음 |
| 자동화·대량 제출·의심 요청 | 인증 입구에서 차단·rate limit·짧은 보안 로그 보관 | 보안 대응과 가격 관측 저장을 분리함 |
| 사용자 지원 또는 가격 이의 제기 | 사용자가 기기에서 원본을 확인하고 수정한 최소 관측값을 다시 제출 | 운영자가 영수증을 열람·보관하지 않음 |

새로운 예외가 정말로 원본 또는 제출자와 관측값의 연결을 요구한다면, 기능으로
바로 추가하지 않는다. 별도 데이터 정책, 명시적 동의, 보유·삭제 기간, 접근 권한,
재식별 위험 검토를 먼저 결정하고 이 문서와 결정 로그를 갱신한다. 해당 예외는
기존 관측 데이터에 소급해서 사용자·영수증 연결을 만들 수 없다.

## 8. 현재 구조에서의 변경 방향

현재 공개 관측 생성 경로는 `receiptId`, `receiptItemId`, `observedAt`을 관측에
연결하고, 영수증 단위 입력에서 공개 관측을 만든다. 이 설계가 구현되면 다음
방향으로 바꾼다.

1. 영수증·항목 식별자와 구매 시각을 서버/공개 관측 스키마에서 제거한다.
2. 전체 영수증 JSON을 서버의 입력·검토·공개 데이터로 사용하지 않는다.
3. 클라이언트가 로컬 OCR 결과에서 최소 관측 payload만 만들어 전송한다.
4. 공개 관측의 식별성과 중복 병합은 영수증 키가 아닌 관측 의미 키로 처리한다.
5. 판매처는 OCR 원문 문자열이 아니라 정규화된 판매처 마스터에 연결한다.
6. 영수증 품질 검토가 필요할 경우에도 서버에 원본을 올리는 대신, 로컬에서의
   사용자 확인과 최소 관측값의 형식·이상치 검증을 우선한다.

이 문서는 향후 구현 방향을 정한 것이다. 현행 코드가 이 경계를 이미 만족한다는
의미는 아니다.

## 9. 수용 기준

구현 완료로 판단하려면 다음을 확인한다.

- 서버 DB, API payload, 공개 JSON, 오류 추적, 분석 이벤트에서 이미지·전체 OCR JSON·영수증 ID·항목 ID·거래 시각을 찾을 수 없다.
- 하나의 로컬 영수증에 담긴 여러 상품이 서버에서 같은 영수증으로 그룹화되지 않는다.
- 동일한 판매처·날짜·상품/규격·가격 제출은 영수증/제출 카운트를 만들지 않고 하나의 가격 관측으로 병합된다.
- 로컬에서 이미 처리한 영수증은 다시 전송할 수 없고, 네트워크 재시도도 중복 관측을 만들지 않는다.
- 인증·rate limit이 동작하지만, 저장된 가격 관측에서 제출자를 역추적할 수 없다.
- 판매처 상세·통계·관리 화면에 영수증 수 또는 제출자 수가 표시되지 않는다.

## 10. 남은 결정

- 로그인 계정, 단기 익명 자격증명, 또는 다른 방식 중 어떤 인증 수단을 사용할지
- 허위·오인식 가격을 걸러내는 이상치 규칙과 사용자 수정 UX
- 판매처 주소를 어느 공개 지도 데이터와 어떤 검수 흐름으로 정규화할지
- 희소·민감 판매처의 공개 지연 또는 지역 단위 축약 기준
- 로컬 원본의 기기 교체·삭제·백업 UX
